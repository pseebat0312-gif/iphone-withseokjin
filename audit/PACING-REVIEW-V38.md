依据网站源码第37版（1e124b98f0e0890ca469f4b4b78a9bf1989f0a2a），不依据旧GitHub main。2026-10-26用户随后明确确认钢琴前移并直接上线。

## 原本真实顺序

初识：intro-v → intro-table（12页聚餐）→ intro-contact → intro-jin → intro-days → spark。
暧昧开局：直接 spark。随后 r-invite → r-arrive。改期分支经过 r-reschedule。

咖啡馆 r-arrive / r-seat / r-order / r-door / r-cafe-close / r-confess / r-first-couple 被20页长场景合并演出。第12页附近的接受/暂缓触发真实节点选择，结尾会连续完成相应短节点。不是每个短节点都单独呈现一次。这是“几分钟就恋爱”的实际机制原因。

恋爱后：到家聊天 → 泰亨/柾国的知情与朋友分支 → 早安 → 书妍展览与玩家生活选择 → 放映室或做饭 → X灯牌猜测 → IG请求 → 聚餐/独处 → 泰亨露台、硕珍露台 → 工作冲突与展览 → 陌生来电 → D-Report拼图 → 共同处理/告知可信的人 → 更正 → 重逢、拥抱 → 钢琴 → 柾国当面或文字告白 → 硕珍接应 → 海边或在家 → 朋友线收束 → 不同幸福结局 → 14组固定日常/12套可重玩约会/自由聊天。

## 钢琴两处可控差异

在原定义上保留全部cue。新暧昧状态仅替换两条**显示文字**：
- 原“明明已经在一起了……”改为尚未说破的心事。
- 原“海边的行程在明天……”改为明天还想再见的念头。

自动字幕先生成原版时间表，再替换这两条字符串，`at`逐项不变，不因字数变化重新分配整首歌。旧情侣存档显示原文。

## 78组用户修订可见性

47组主线聊天节点均可从两种开局之一到达；14组日常在结局后按原机制送达；17组额外内容位于公开评论、请求、短信、来电及购物模板。职业版本/拒绝与接受分支互斥，因此不会一次游玩全部出现，不能为了“都出现”让同一人物前后说两种相反结果。

真正漏显示的原因包括：spark、r-ig-request为igdm而KKT过滤；r-x-read放在X页面当私聊；旧存档已有作者消息不会自动补新增行、删掉超出新数组的旧行。本轮分别修正路由、旧记录清理/补行，并保留自由聊天与原选择状态。

r-piano-invite的原用户文字继续存档保存，已是情侣的旧路线仍使用；新暧昧路线用时间语义适配的邀请，避免“明天海边”与第二天咖啡馆冲突。
